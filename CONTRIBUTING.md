# Contributing

Rules for sending an issue or a PR to goo-button.

## Before you start

For a bug or an idea, open an issue first if one doesn't exist yet. For a small fix (typo, minor bug) you can go straight to a PR.

## Set up the project

You need Node 22 or newer and pnpm.

```sh
git clone https://github.com/dukxa/goo-button.git
cd goo-button
pnpm install
```

Run the demo:

```sh
pnpm demo
```

It opens at http://localhost:5173/demo/.

## Tests

Run the full test suite before sending a PR:

```sh
pnpm test:full
```

This runs unit tests, the typecheck, the build, and e2e tests (skipping Firefox when it's not needed). You can also run each piece on its own:

```sh
pnpm test        # unit tests (node --test)
pnpm typecheck    # type check
pnpm build        # build the package
pnpm test:e2e     # e2e tests through Playwright
```

If you touched anything under `package/src/`, `test/`, or `e2e/`, `pnpm test:full` is required before the PR.

## Generated files

`package/goo-button.min.js` and the demo build files (`demo/src/goo-button.js`, `demo/src/highlight.min.js`) are generated by `pnpm build` and `pnpm build:demo`. Don't edit them by hand. If you need to change behavior, change the source in `package/src/` and run the build instead of touching the output.

## Documented limitations

Some things in `docs/usage.md#limits` (for example, the drop not mirroring for RTL, or not reserving space for it) are intentional, not bugs. If you want to change that, open an issue and discuss it first, before sending a PR.

## Code style

Match the style already in the file you're editing. There's no separate linter in the project, so look at the surrounding code.

## Pull requests

- One PR, one change. Don't mix a refactor with a new feature.
- Describe what changed and why in the PR description.
- If the PR closes an issue, say so (`Closes #123`).
- Make sure `pnpm test:full` passes before you send the PR.
