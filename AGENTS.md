# AGENTS.md

Instructions for AI coding agents (Claude Code, Codex, Cursor, Copilot, Windsurf, etc.)
working in this repository. Read this before making changes.

## What this repo is

`goo-button` is a **zero-dependency ES module** that progressively enhances a real
`<button>` (or `role="button"`) marked with `data-goo`: on hover/focus it pulls an
animated SVG "drop" out of the button's edge, with a slotted icon riding inside it.
It is **not** a custom element and **not** a framework component — no new tag, no
Shadow DOM, no `innerHTML`, no build-time framework dependency for consumers.

Two halves live in one pnpm workspace:

- **`package/`** — the publishable npm package (`goo-button`). This is the product.
- **`demo/`** — a static demo site (sliders, color pickers, code generator) deployed
  to GitHub Pages from `demo/`. Not published to npm.

Root `package.json` is private and only holds dev tooling for the whole workspace.

## Non-negotiable constraints

These are deliberate design decisions. Do not "fix" them without being asked:

1. **No dependencies, ever**, for `package/src/*`. No network requests, no fonts, no
   icon libraries, no `innerHTML`, no `eval`. Keeping `goo-button` dependency-free is
   a stated feature (see README "No dependencies").
2. **It decorates real buttons; it is not a custom element.** Don't suggest converting
   it to a Web Component / Lit / React component inside `package/src`. The whole point
   (see `docs/faq.md`) is that the element stays a real `<button>`.
3. **Strict CSP / Trusted Types compatibility.** No inline styles in markup; CSS is
   injected via a constructed stylesheet (`adoptStyles` in `dom.js`) using
   `CSSStyleSheet.replaceSync` + `adoptedStyleSheets`. Don't reintroduce `style="..."`
   attributes or `<style>` tags into component code.
4. **Attribute values are validated, not trusted**, because they're interpolated into
   CSS custom properties (see `tokens.js` and `docs/configuration.md#how-values-are-checked`).
   Any new `data-goo-*` option needs the same type/range checking pattern — never pass
   a raw attribute value into `style.setProperty` without validation.
5. **Feature-detected, not polyfilled.** The `supported` check at the top of
   `goo-button.js` gates everything. If a required API is missing, the module does
   nothing and the plain `<button>` stays usable. Don't add polyfills; extend the
   detection instead.
6. **The drop always opens to the right; RTL/vertical writing modes are not mirrored.**
   This is a documented limitation (`docs/usage.md#limits`), not a bug to silently fix.
7. **`package/goo-button.min.js` and `demo/src/goo-button.js` and
   `demo/src/highlight.min.js` are build output.** Never hand-edit them — edit
   `package/src/*` or `tools/demo-highlight/*` and rebuild. The build script also
   rewrites version pins and byte-size badges inside `README.md` and `docs/faq.md`;
   don't hand-edit those `<!--size:...-->` markers either.
8. **JSDoc types, not TypeScript source.** `package/src/*.js` is plain JS with JSDoc
   annotations, checked via `tsc --checkJs` (see `tsconfig.json`). Don't convert files
   to `.ts` — `goo-button.d.ts` is hand-written separately and checked by
   `tsconfig.types.json`.

## Commands

Requires Node >=22 and pnpm (see `packageManager` field in root `package.json`; run
`corepack enable` if pnpm isn't available).

```sh
pnpm install              # install workspace deps
pnpm demo                 # dev server -> http://localhost:5173/demo/
pnpm test                 # unit tests (node --test test/*.test.mjs)
pnpm typecheck             # tsc over package/src (JSDoc-checked) and goo-button.d.ts
pnpm build                 # esbuild -> package/goo-button.min.js (+ syncs README/faq badges)
pnpm build:demo            # esbuild -> demo/src/goo-button.js, demo/src/highlight.min.js
pnpm test:e2e               # Playwright, all browsers (chromium/firefox/webkit)
pnpm test:e2e:no-firefox    # Playwright without firefox (faster local loop)
pnpm test:full              # test + typecheck + build + test:e2e:no-firefox — run before a PR
pnpm browser-support         # checks README's claimed browser matrix against real compat data
pnpm pack:lib                # npm pack inside package/ (runs prepack first)
```

**Before opening a PR or claiming a task is done, run `pnpm test:full`.** It mirrors
what CI effectively needs and catches type errors, broken unit tests, build failures,
and visible browser regressions in one shot.

## Workflow notes for agents

- **Edit source, then rebuild** — if you change anything under `package/src/`, run
  `pnpm build` so `package/goo-button.min.js` stays in sync, and `pnpm build:demo` if
  the demo should reflect it too. A PR with source changes but a stale `.min.js` is wrong.
- **Pure logic goes in `shape.js` / `spring.js`**, which are what `test/*.test.mjs`
  cover. Keep them framework- and DOM-free (no `document`, no `window`) so they stay
  easily unit-testable.
- **DOM/CSS structure lives in `dom.js`** (`STYLES` template string + `buildDom`).
  The build script's `squeezeCss` step strips comments/whitespace from that exact
  `const STYLES = \`...\`` block — don't rename that constant or change its shape
  without checking `tools/build/build.mjs`'s `squeeze()` regex still matches.
- **New `data-goo-*` attributes**: add parsing/validation in `tokens.js`
  (`OPTIONS`/`DATA_ATTRS`/`parseValue`/`GEOMETRY_TOKENS` as appropriate), wire it in
  `goo-button.js#applyAttr`, document it in `docs/configuration.md`'s table, and add a
  type to `goo-button.d.ts` if it affects the public API.
- **Docs are user-facing contracts.** If you change attribute defaults, ranges,
  browser support, or behavior described in `docs/*.md` or `README.md`, update the
  prose to match — these docs are read literally by consumers, not just as hints.
- **Don't hand-edit generated size/version markers.** `pnpm build` regenerates the
  `<!--size:min-->...<!--/size-->` badges and the `goo-button@x.y.z` CDN version pins
  in `README.md`/`docs/faq.md`/`demo/index.html` from `package/package.json`'s version.
  Bump the version there, then build — don't sed the badges by hand.
- **The demo is a separate CSP-strict static site**, bundling the library same-origin
  (see comment in `build-demo.mjs`) rather than loading it from a CDN. Demo code
  (`demo/src/app.js`, `app.css`) is not part of the published package and can use
  patterns the component itself avoids (e.g. it's fine for demo code to be less
  defensively validated than `package/src`).
- **Accessibility is tested, not assumed.** `e2e/axe.spec.mjs` runs axe-core against
  the demo. Keep ARIA semantics (`aria-hidden` on decorative SVG/icon wrapper, focus
  handling, `:focus-visible` ring, `disabled`/`aria-disabled` handling) intact when
  touching `goo-button.js` or `dom.js`.
- **Commit messages / PRs**: this is a small, deliberately minimal library — prefer
  the smallest diff that satisfies the request over refactors, added dependencies, or
  new abstractions that aren't asked for.

## Key docs to read before non-trivial changes

- `README.md` — feature overview, install snippet, browser support matrix.
- `docs/usage.md` — the fullest behavioral spec (fonts, colors, icon slot, states,
  focus ring, reduced motion, framework/shadow-DOM integration, known limits, security).
- `docs/configuration.md` — every attribute/token and its validation rule.
- `docs/api.md` — the complete JS API surface (it's intentionally tiny).
- `docs/faq.md` — *why* decisions were made (size, no custom element, why JS not CSS).
  Read this before proposing an architecture change.
